# Antigravity Truth Guard: 5 Універсальних Глобальних Законів

## Закон 1: Обґрунтований контекст (global-no-guessing)
Будь-якому ШІ-агенту чи розробнику суворо заборонено вгадувати, галюцинувати або екстраполювати архітектуру кодової бази, схеми баз даних, контракти API чи бізнес-правила. Перед початком будь-якого планування чи написання коду агент ЗОБОВ'ЯЗАНИЙ викликати `truth_search` для отримання підтверджених специфікацій. Якщо специфікація відсутня в базі, агент повинен перепитати користувача або явно позначити поле як невідоме/null, замість вигадування довільних схем.

## Закон 2: Міжсегментна ізоляція (global-surgical-scope)
Строгі межі Чистої Архітектури (Clean Architecture) повинні дотримуватися в кожній задачі. Один промпт або коміт НІКОЛИ не повинен змішувати зміни між різними архітектурними сегментами (Доменне ядро, Сценарії використання / Application, Інфраструктура / База даних, Доставка / HTTP-адаптери, Представлення / UI). Якщо функціонал вимагає змін у кількох шарах, агент зобов'язаний декомпозувати задачу на послідовні кроки, забезпечуючи нуль помилок компіляції (`Zero-Diagnostic Rule`) та 100% проходження тестів перед переходом до наступного кроку.

## Закон 3: Чесність верифікації та незмінність специфікацій (global-verification-honesty)
Перевірку плану категорично заборонено фальсифікувати, імітувати чи обходити. Кожен план, що подається до `truth_verify_plan`, повинен явно посилатися на автентичні `cited_fact_ids` із `truth_search` та містити список `target_files`. Квитанції верифікації є криптографічно підписаними HMAC-токенами з обмеженням дії 15 хвилин, прив'язаними до `target_files` та одноразовими для кожного коміту. Зміна або додавання правил через `truth_upsert_rule` суворо вимагає підтвердження людиною (Human-in-the-Loop через одноразовий токен); агентам заборонено самовільно змінювати специфікації проєкту. Скрипти верифікації проєкту (такі як `check-receipt.mjs`, git pre-commit hook та `npm run verify`) суворо контролюють свіжість та криптографічну цілісність квитанції перед створенням коміту чи білду. Пропуск діагностики компілятора (`tsc --noEmit`), відключення тестів чи використання неперевірених чеків суворо заборонено. Якщо `truth_verify_plan` повертає `approved: false`, агент зобов'язаний негайно зупинитися та виправити план.

## Закон 4: Бухгалтерський облік (global-defensive-code)
Усі фінансові та грошові суми повинні виражатися виключно в цілих копійках (`integer cents`). Арифметика з плаваючою комою (float) для грошей суворо заборонена. Фізичні та зарезервовані залишки ніколи не перезаписуються абсолютними числами; будь-яка зміна є незмінною дебетовою або кредитовою проводкою в обліковому журналі з обов'язковою наявністю підтверджуючого документа.

## Закон 5: Ієрархія правди (global-project-priority)
У будь-якій ситуації, коли специфічне правило проєкту (`project_id != 'global'`) конфліктує із загальним глобальним правилом, правило проєкту має абсолютний пріоритет (`priority: HIGH (PROJECT OVERRIDE)`). Глобальні правила є захисними рамками за замовчуванням (`priority: BASE (GLOBAL)`), тоді як локальні доменні правила визначають конкретну семантику програми.
