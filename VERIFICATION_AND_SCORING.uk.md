## 1. Загальна філософія: Принцип "Наряду-допуску" (Work Permit)

У традиційній розробці ШІ-агенти пишуть код «з голови», спираючись лише на внутрішню пам'ять нейромережі. Якщо агенту бракує контексту (наприклад, точної назви стовпця в PostgreSQL або правила округлення грошей), він починає **вгадувати** (галюцинувати).

**Antigravity Truth Guard** впроваджує модель промислового технічного нагляду:

```
┌──────────────┐     1. truth_search     ┌──────────────────────────────────┐
│              ├────────────────────────>│  RAM Mirror (База знань фактів)  │
│              │<────────────────────────┤  (0 читань з платної БД)         │
│   ШІ-Агент   │     2. Точні факти      └──────────────────────────────────┘
│              │
│              │     3. truth_verify_plan┌──────────────────────────────────┐
│              ├────────────────────────>│  Незалежний LLM-Аудитор          │
│              │                         │  (Zero-Tolerance Auditor)        │
│              │<────────────────────────┤                                  │
│              │     4. approved + чек   └──────────────────────────────────┘
└──────┬───────┘
       │ 5. Редагування дозволених target_files
       ▼
┌────────────────────────────────────────────────────────┐
│  Шлюз перевірки перед комітом (check-receipt.mjs)       │
│  • Перевіряє підпис HMAC-SHA256                        │
│  • Перевіряє TTL (не старіше 15 хвилин)                │
│  • Перевіряє, що змінено ТІЛЬКИ затверджені файли      │
└────────────────────────────────────────────────────────┘
```

Агент не може змінити жодного рядка коду без криптографічно підписаної квитанції-допуску (`.truth-receipt.json`).

## 2. Що таке `0.5` при пошуку та як працює формула релевантності (`truth_search`)

Коли агент викликає `truth_search`, система шукає правила у пам'яті (RAM Mirror) та повертає масив фактів із числовим балом релевантності (`score`):

### Звідки бралося число `0.5`?
У ранніх версіях пошуку, коли векторні індекси ще будувалися або коли пошук працював за спрощеним текстовим фільтром, кожному знайденому за ключовими словами чанку присвоювалася фіксована базова оцінка: **`score: 0.5`** (тобто 50% базова релевантність). Це була статична заглушка.

### Як скорінг пошуку працює зараз (у версії v2.1.0)?
Починаючи з v2.1.0, оцінка релевантності пошуку розраховується динамічно за гібридною формулою **Cosine Similarity (70%) + Keyword Bonus (30%) + Priority Multiplier**:

$$\text{FinalScore} = \min\Big(1.0, \big(\text{CosSim} \times 0.70 + \text{KeywordBonus} \times 0.30\big) \times \text{PriorityWeight}\Big)$$

1. **Семантична схожість (Cosine Similarity, 70% ваги):**  
   Запит агента та кожен фрагмент правил перетворюються моделлю `models/gemini-embedding-001` на щільні векторні ембеддінги розмірністю 768 чисел. Система вираховує косинусний кут між вектором запиту $\vec{A}$ та вектором факту $\vec{B}$:
   $$\text{CosSim} = \frac{\vec{A} \cdot \vec{B}}{\|\vec{A}\| \|\vec{B}\|}$$
   Якщо агент запитує *"як рахувати собівартість при списанні"*, а правило називається *"FIFO Valuation & Cost Allocation"*, векторна схожість покаже високий бал (~0.75–0.85), навіть якщо слова різняться.
2. **Лексичний збіг слів (Keyword Bonus, 30% ваги):**  
   За кожне значуще слово із запиту (>2 символів), яке точно зустрічається у заголовку або тексті правила, нараховується бонус `+0.15`.
3. **Ієрархія пріоритетів (`PriorityWeight`):**  
   Згідно з Законом 5 (Hierarchy of Truth), правила конкретного проєкту мають безумовну перевагу над загальними:
   * **Правило проєкту (`project_id === currentProject`):** Множиться на `1.05` і отримує маркер `HIGH (PROJECT OVERRIDE)`.
   * **Глобальне правило (`project_id === 'global'`):** Множиться на `1.00` і отримує маркер `BASE (GLOBAL)`.

Завдяки цьому в оновленій системі агент отримує точні математичні оцінки (`0.7457`, `0.6053`, `0.4903` замість однакового `0.5`).

## 3. Покроковий життєвий цикл верифікації плану (`truth_verify_plan`)

Процес верифікації плану виконується у 5 суворих кроків:

1. **Крок 1: Обов'язкове вивчення креслень (`truth_search`)**  
   Агент зобов'язаний за Законом 1 (Grounded Context) знайти офіційні правила. Результатом є перелік знайдених правил з їхніми унікальними ідентифікаторами (`fact_id`), наприклад:
   `sklad:docs/RULES.md#14-ledger-first--`
2. **Крок 2: Формування та подання плану**  
   Агент формує запит до інструменту `truth_verify_plan`, обов'язково вказуючи:
   * `proposed_plan`: детальний покроковий опис того, що він збирається зробити в коді.
   * `cited_fact_ids`: список ідентифікаторів правил, які він процитував.
   * `target_files`: **суворо обов'язковий непорожній масив** шляхів до файлів, які агент збирається редагувати або створювати.
3. **Крок 3: Перевірка плану незалежним LLM-аудитором**  
   Запит надходить до мовної моделі Gemini Flash. Моделі передається роль суворого аудитора зі спеціальним системним промптом:
   > *"Ти — строгий аудитор з нульовою толерантністю до галюцинацій. Перевір, чи кожен крок, таблиця бази даних, назва поля, статус enum та бізнес-формула суворо обґрунтовані наданими фактами. Якщо план вигадує будь-що непідтверджене — негайно відхиляй."*
   Модель отримує **виключно два блоки тексту**: текст процитованих правил і текст плану.
4. **Крок 4: Криптографічний підпис квитанції**  
   Якщо аудитор схвалив план, сервер створює цифровий підпис за алгоритмом HMAC-SHA256:
   $$\text{Signature} = \text{HMAC-SHA256}_{\text{Key}}(\text{project\_id} : \text{plan\_hash} : \text{target\_files} : \text{timestamp} : \text{cited\_facts})$$
   Квитанція зберігається у файл `.git/.truth-receipt.json` (або в корінь проєкту). Термін її дії — **суворо 15 хвилин**.
5. **Крок 5: Контроль на виході (`check-receipt.mjs`)**  
   Перед комітом або білдом скрипт перевіряє квитанцію. Якщо вона відсутня, прострочена, має підроблений підпис або агент змінив файл, якого не було в `target_files`, — процес завершується з помилкою `exit(1)`.

## 4. Шкала та критерії скорінгу аудитора (від 0.0 до 1.0)

Під час перевірки плану мовна модель-аудитор повертає оцінку якості та обґрунтованості плану:

```json
{
  "approved": true,
  "score": 1.0,
  "hallucinations_or_missing_conditions": [],
  "receipt_token": "TG-VERIFIED-a1b947c6ec80"
}
```

### Шкала оцінок:

| Оцінка (`score`) | Вердикт | Що це означає |
|---|---|---|
| **`1.0`** | **APPROVED** | **Бездоганна відповідність.** Кожен пункт плану, назва моделі, стовпчик та формула на 100% підтверджені процитованими правилами. Масив зауважень порожній. |
| **`0.7` – `0.89`** | **REJECTED** | **Часткова відсутність фактів.** План виглядає логічним, але спирається на припущення, які відсутні у процитованих фактах. Наприклад, якщо агент планує зв'язування клієнтів за номером телефону, але процитував лише правило про собівартість товарів, аудитор ставить `0.7` та відхиляє план. |
| **`< 0.5`** | **REJECTED** | **Груба невідповідність / галюцинація.** План суперечить архітектурі, намагається вимкнути перевірки (`@ts-ignore`), пропустити тести або вигадує власні фінансові формули. |
| **`0.0`** | **HARD REJECT** | **Автоматичне блокування.** Порожній список `target_files`, відсутність процитованих фактів або порушення протоколу взаємодії. |

## 5. Інваріант трьох замків: Коли план отримує `approved: true`

Щоб виключити випадкові схвалення, у системі діє непорушний закон трьох перевірок:

> [!IMPORTANT]
> План отримує вердикт `approved: true` **виключно тоді, коли одночасно виконано всі три умови**:
> 1. $\text{score} \ge 0.9$ (оцінка відповідності 90% або вище).
> 2. `hallucinations_or_missing_conditions.length === 0` (масив зауважень абсолютно порожній).
> 3. `target_files` — валідний непорожній список цільових файлів.

Якщо аудитор знайшов **хоча б одне** зауваження, навіть якщо `score: 0.85`, вердикт автоматично стає `approved: false`, токен квитанції отримує префікс `TG-REJECTED-xxxx`, а запис дозволу в `.truth-receipt.json` блокується.

## 6. Захист від збоїв: Режим Fail-Closed Fallback

Що відбувається, якщо Інтернет зник, квота Gemini API вичерпана або спрацював захисний вимикач (Circuit Breaker)?

* **Як було раніше (Вразливість):**  
  Локальний fallback перевіряв лише відсутність слів `@ts-ignore` та видавав підписаний квиток `approved: true`, фактично дозволяючи неперевірені зміни.
* **Як працює у версії v2.1.0 (Fail-Closed):**  
  Локальний режим переведено у статус захисту від відмов (**Fail-Closed**):
  1. Локальний режим **категорично не видає схвалених квитанцій** автоматично (`approved: false`, статус `UNVERIFIED_FALLBACK`).
  2. Видається попередження з одноразовим токеном запиту людського втручання:
     `"STOP: Truth Guard is operating in LOCAL_FALLBACK mode... requires human authorization. override_token: 'OVERRIDE-xxxxxxxx'"`
  3. Тільки якщо користувач-людина в чаті явно підтвердить план і агент передасть `human_override: true` та правильний токен `override_token`, система видасть дозвіл із позначкою `tier: LOCAL_FALLBACK_HUMAN_OVERRIDE`.

## 7. Контроль на виході: Шлюз `check-receipt.mjs` та захист меж файлів

Останній бар'єр захисту спрацьовує безпосередньо в репозиторії розробника через Git pre-commit hook або команду `npm run verify`:

1. **Сувора перевірка меж файлів (Boundary Safety):**  
   Звірка змінених у Git файлів здійснюється за правилом точного збігу або межі каталогу зі слешем:
   ```javascript
   const isMatch = normalizedTargets.some(target => {
     const boundaryTarget = target.endsWith('/') ? target : target + '/';
     return normFile === target || normFile.startsWith(boundaryTarget);
   });
   ```
   Це гарантує, що дозвіл на файл `src/auth` ніколи не дозволить змінити `src/author.ts`.
2. **Одноразовість квитанції (Single-Use Token):**  
   Під час успішного коміту квитанція позначається як використана (`consumed: true`). Наступний коміт вимагає нового виклику `truth_verify_plan`.
3. **Обмеження за часом (15m TTL):**  
   Якщо між схваленням плану та спробою коміту минуло понад 15 хвилин, квитанція вважається простроченою, і агент зобов'язаний підтвердити план повторно.
